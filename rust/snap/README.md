# snap

极简项目版本快照工具。单个可执行文件，没有运行时依赖。

```bash
cargo build --release      # 产物: target/release/snap.exe（约 450 KB）
cargo test                 # 单元测试 + 命令行集成测试（共 30 项）
```

还有一个在真实目录上跑的场景测试（108 项检查，会重建沙箱目录；需要 git-bash）：

```bash
bash tests/scenario.sh                        # 默认沙箱: 项目里的 test/
SNAP_SANDBOX=/tmp/xxx bash tests/scenario.sh  # 也可以指定别的沙箱目录
```

## 用法

```bash
cd 你的项目
snap -i                        # 初始化（生成 .snap 目录和命令对照表）
snap -t                        # 看工作区改了什么
snap -s "完成登录功能"           # 保存一个版本
snap -l                        # 看历史
snap -c a55b                   # 切回某个版本（前几位前缀即可）
snap -d a55b                   # 某个版本 vs 现在的工作区
```

短写法、首字母、完整写法三者等价：`snap -s "说明"` = `snap s "说明"` = `snap save "说明"`。
版本ID可以只写前几位前缀。初始化后完整的命令对照表在 `.snap/命令对照表.md`，
也可以随时 `snap -h` 查看。

命令在项目的任意子目录里都能用，会自动向上找到项目根的 `.snap`。

## 安全机制

`-c`（切换版本）会覆盖文件，所以有三道保护：

- **会丢内容时先确认**：工作区里有没保存到任何版本的内容时，先列出来再问
  `继续? [y/N]`，回车或答 n 就取消，一个文件都不会动；在 CI / 管道里没有可读的
  stdin 时按取消处理，绝不替你猜 y。
- **执行前预检**：对象库缺对象、目标路径被同名目录占住、上层路径是文件、
  文件只读等问题一次性列出来，**在动任何文件之前**退出。
- **不留半成品**：只有全部成功才更新当前版本指针；中途失败会明确报告哪些文件
  处理失败，并提示重新运行。

## 依赖

只用了四个成熟库，其余逻辑都自己实现：

| 库 | 用途 |
| --- | --- |
| `flate2` | zlib 压缩/解压（对象库里的 blob） |
| `sha1` | 内容哈希与版本ID |
| `serde_json` | 解析版本 JSON（写出由自己实现，保证格式稳定） |
| `chrono` | 本地时间格式化 |

## 磁盘格式

```
.snap/HEAD                       当前版本ID（12 位十六进制，或空）
.snap/versions/<id>.json         版本记录 {parents, tree, message, time, seq}
.snap/seq                        递增序号（同一秒内排序用）
.snap/objects/<前2位>/<余38位>     文件内容，zlib 压缩，文件名为 sha1(原始内容)
.snap/命令对照表.md                init 时生成的命令对照表
```

- **版本ID** = `sha1(紧凑JSON)` 的前 12 位，载荷是
  `{"message":…, "parents":[…], "tree":{…}}`，键排序、`", "` 与 `": "` 分隔、
  非 ASCII 不转义。载荷不含时间，所以相同状态重复保存不会产生垃圾版本。
- **tree** 的值是 `sha1(文件原始内容)`；对象文件是 zlib 压缩后的内容。
  相同内容全库只存一份。
- **路径键**一律用 `/` 分隔，所以仓库可以跨平台复制。
- 旧名字 `.vsnap` / `.vsnapignore` 仍然识别，`init` 时会把数据目录改名成 `.snap`。
- **对象有两种物理格式**，读的时候自动识别，可以共存：
  小文件是**一条 zlib 流**；8MB 以上的大文件是**分块容器**（magic `SNPCHUNK`，
  4MB 一块，每块独立 zlib，前面带一张偏移表），这样压缩能并行。
  两者的对象名都是 `sha1(原始内容)`，所以版本数据与去重逻辑完全不受影响。

## 忽略规则（`.snapignore`，放在项目根目录）

```
*.log          不含 "/" 的模式，匹配任意一层里的同名条目
logs/          以 "/" 结尾表示目录规则，匹配该目录及其下所有内容
keep/c.txt     含 "/" 的模式相对项目根目录定位，"*" 不跨目录层级
src/**/*.py    "**" 可跨任意层级
# 开头的行和空行忽略；不支持 "!" 反选
```

默认已经忽略：`.snap/` `.vsnap/` `.git/` `__pycache__/` `*.pyc` `*.pyo`
`.DS_Store` `*.swp` `*~`。此外**正在运行的这个程序文件自己也不会进版本库**，
所以把 `snap.exe` 放在项目里也没关系。

## 性能

在 32GB 内存 / SSD 的 Windows 上用**真实数据**实测（`test/iso` 里的系统镜像）：

| 操作 | 数据量 | 耗时 | 吞吐 | 峰值内存 |
| --- | --- | --- | --- | --- |
| `-t` 首次扫描（冷索引，必须全量哈希） | 15 GB | 10 秒 | ~1.5 GB/s | 很小 |
| `-t` 再次扫描（有索引，跳过未变文件） | 15 GB | **0 秒** | — | 很小 |
| `-s` 保存（扫描 + 压缩 + 落盘） | 15 GB | **17 秒** | ~880 MB/s | **43 MB** |
| `-c` 切回（解压 + 写文件） | 1.4 GB 单文件 | 3 秒 | ~470 MB/s | **6 MB** |
| `-l` / `-v` 看历史、看版本详情 | — | 瞬间 | — | 很小 |

按这个吞吐推算，76GB 级别的目录一次完整保存约 **1.5 分钟**（最初一版要 13 分钟以上）。

几点说明：

- **索引让重复操作几乎免费**：`.snap/index` 记录每个文件的 大小、修改时间、**变更时间
  （ctime）** 和内容哈希，没变过的文件不再重新读盘，保存时连压缩也跳过（对象已在库里）。
  15GB 目录第二次 `-t` 是 0 秒（此前每次要 125 秒）。
  判定规则参照 git 的索引：三个字段都一致、**而且**修改时间早于索引写入时刻
  （git 的 racy 规则）才信任缓存。所以即使有工具在改内容的同时把修改时间改回去
  （`touch -r`、`cp -p`、`rsync -t`……），ctime 变了照样会被发现——
  这条有常驻回归测试（`tests/scenario.sh` 的 11b）。`SNAP_NO_INDEX=1` 可完全不用索引。
  代价：Windows 上取 ctime 需要额外打开一次文件（实测 2000 个文件热扫描 215 ms，
  约 0.1 ms/文件）；Unix 上 ctime 由 stat 直接给出，没有额外开销。
- **内存与文件大小无关**：读写都是流式的（边读边哈希边压缩、边解压边写），
  所以 11GB 的镜像也只占几 MB 内存。
- **压缩分三档**，目标是"该压的压、压不动的别浪费时间"：
  1. 小于 4MB 的文件用级别 6（源码/文本，压得狠且开销可忽略：100MB 文本 →
     33.2MB，级别 1 只能到 43.9MB）。
  2. 大文件先用均匀 16 段取样试压，取**中位数**收益；省不到 10% 就直接存储
     （zlib 级别 0）。为什么不能只看开头：ISO 头部元数据能压掉 77%，整个文件
     其实只有 2.9%，只看开头会把时间全浪费在无效压缩上（实测 15GB 保存从
     165 秒降到 57 秒，代价是对象库体积 +4%）。
  3. 其余大文件用级别 1。
  相关旋钮都在 `src/store.rs`：`COMPRESSION_LEVEL_SMALL` / `COMPRESSION_LEVEL_BIG` /
  `BIG_FILE_BYTES` / `SAVE_MIN_GAIN`（调小更省空间，调大更快）。
- **大文件分块并行压缩**：zlib 是单线程的，压缩是保存时的唯一瓶颈，所以 8MB 以上的
  文件会按 4MB 分块、交给多个线程一起压，装进一个自描述的容器（magic `SNPCHUNK`）。
  15GB 的保存从 57 秒降到 17 秒。线程数默认取 CPU 并行度、上限 8，可用 `SNAP_THREADS` 覆盖。
  代价是内存从几 MB 变成"线程数 × 块大小"（默认约 40MB，仍然与文件大小无关）。
  旧仓库里"单条 zlib 流"的对象照常能读——读的时候先嗅探 magic。
- **进度提示**：保存和扫描时在终端显示 `扫描中 12/29 个文件, 43.2 GB, 跳过 8 个未变文件`，
  只在真实终端显示，管道与重定向时保持安静。
- 保存已压缩数据（镜像、视频）时对象库体积≈原体积，也就是磁盘占用基本翻倍，
  这类素材更适合放进 `.snapignore` 只对源码做版本管理。

## 模块

| 文件 | 内容 |
| --- | --- |
| `src/main.rs` | 入口、参数解析、八个命令、checkout 的预检与执行 |
| `src/store.rs` | 仓库定位、对象库、版本读写、工作区扫描、版本ID |
| `src/chunk.rs` | 大文件的分块容器与多线程并行压缩 |
| `src/ignore.rs` | `.snapignore` 规则编译与匹配 |
| `src/docs.rs` | 命令清单（解析器、帮助、对照表同源） |
| `src/winout.rs` | Windows 控制台按 UTF-16 输出，重定向时输出 UTF-8 |
| `tests/cli.rs` | 命令行集成测试（对编译出来的二进制做黑盒测试） |
| `tests/scenario.sh` | 在真实目录上按使用顺序跑一遍的场景测试（108 项检查） |

## 已知取舍

- 版本历史是线性的，没有分支、合并、推送；`gc` 在正常使用中基本无事可做，
  只在对象库有残留时才起作用。
- `save` 会读取整个文件内容再压缩，单文件很大时内存占用随之上升。
- 文件名不是合法 UTF-8 的条目会被跳过并给出警告。
- `--help` 的 usage 行固定不折行。
